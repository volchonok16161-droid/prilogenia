# Приёмочное тестирование офлайн-режима на реальном устройстве

Этот сценарий предназначен для отдельного тестового аккаунта и тестовых чек-листов. Не используйте рабочие записи сотрудников.

## Ограничения запуска

- Проверять только на отдельном preview/test deployment после явного разрешения владельца проекта.
- Не выполнять тест на production и не использовать реальные чек-листы.
- Не очищать LocalStorage, IndexedDB, данные браузера или фото до сохранения результатов теста.
- Для сценария отзыва доступа использовать отдельный тестовый аккаунт.
- Не считать локальное восстановление по ключу устройства доказательством действующей Supabase-сессии.

## Подготовка

1. Создать отдельную тестовую учётную запись сотрудника с разрешённой ролью.
2. Подготовить отдельное устройство и браузер с поддержкой IndexedDB, Service Worker и WebCrypto.
3. Открыть тестовый preview по HTTPS, дождаться установки Service Worker и загрузки оболочки.
4. Выполнить первый вход по паролю Supabase.
5. Убедиться, что после первого входа по Email и паролю создан и сохранён неэкспортируемый ключ устройства; отдельный код не запрашивается.
6. Для каждого режима создать отдельный тестовый чек-лист: Комплексный, КМБ, ТТ, БИ и Гидродемпферы.
7. В каждом чек-листе заполнить общие поля, несколько отметок, комментарии, выбранные секции, историю изменений и добавить тестовое фото JPEG/PNG/WebP.

## Матрица сценариев — выполнить для всех пяти режимов

| Проверка | Ожидаемый результат |
|---|---|
| Сохранить онлайн, закрыть и снова открыть браузер | Все поля и фото остаются на месте |
| Включить авиарежим и перезагрузить вкладку | Приложение открывается из установленной PWA-оболочки |
| Открыть приложение без сети на том же устройстве | Открывается только локальный профиль данного устройства |
| Изменить отметку и комментарий офлайн | Изменения остаются после закрытия и повторного открытия |
| Добавить/заменить фото офлайн | Фото остаётся доступным локально после перезапуска |
| Восстановить сеть | Показывается ожидание синхронизации, затем синхронизировано |
| Проверить облачную запись тестового пользователя | Все поля сохранены, фото присутствуют в приватном Storage |
| Выйти и снова войти онлайн на том же устройстве | Чек-лист и фото доступны после восстановления |
| Восстановить чек-лист на чистом тестовом браузерном профиле | Состояние и все фото загружаются из облака |
| Повторить открытие уже восстановленного чек-листа | Нет лишнего резервного снимка и дубликатов фото |

## Дополнительные проверки безопасности и отказов

1. **Неверный дополнительный код:** локальная разблокировка блокируется по настроенному ограничению попыток; данные не удаляются.
2. **Другой сотрудник на том же браузерном профиле:** не получает доступ к локальным данным первого пользователя.
3. **Отозванный/заблокированный тестовый профиль:** после восстановления сети синхронизация останавливается; очередь и локальные данные остаются.
4. **Сеть пропадает во время загрузки фото:** очередь остаётся повторяемой, локальная копия не теряется.
5. **Конфликт ревизий:** локальная и удалённая версии сохраняются отдельно, без автоматического выбора победителя.
6. **Неподдерживаемый формат или фото больше 10 МБ:** загрузка отклоняется с понятной ошибкой; чек-лист не теряется.
7. **Перезапуск во время ожидания синхронизации:** после запуска очередь продолжает обработку без дублирования записи.
8. **Storage недоступен:** облачный payload не должен содержать большие Base64-фотографии; операция остаётся ожидающей повторения.

## Доказательства и критерии завершения

Для каждого режима записать:
- браузер/ОС и версию приложения;
- успешность первого входа и вход по Email и паролюа;
- результат работы офлайн после перезапуска;
- число ожидающих операций до и после reconnect;
- число фото в локальном состоянии, в манифесте и в Storage;
- ревизию облачной записи;
- ошибки консоли/сети без секретов и персональных данных.

Этап считается пройденным только если все пять режимов проходят основные сценарии, фотографии открываются после чистого восстановления, а проверки изоляции и конфликтов не приводят к потере данных.

## Что не проверяется автоматическими тестами

Автоматические CI-тесты моделируют браузерные API и Storage. Они не подтверждают реальную работу Service Worker на конкретном устройстве, поведение iOS/Android при выгрузке вкладки, восстановление после закрытия браузера или реальные RLS-политики проекта. Для этого необходим разрешённый тестовый preview и отдельная тестовая учётная запись.
