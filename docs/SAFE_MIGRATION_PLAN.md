# План безопасного развития чек-листа

## Границы безопасности

- Рабочая версия публикуется из `main`; эта ветка не меняется в рамках аудита.
- Разработка ведётся в `development/safe-updates`.
- Сначала фиксируем текущее поведение и проверяем совместимость; миграция данных не должна запускаться автоматически.
- Никаких реальных паролей, токенов GitHub или секретов в клиентском HTML/репозитории.
- Любое изменение, влияющее на сохранение, импорт/экспорт или синхронизацию, должно иметь проверенный путь восстановления.

## Карта текущего приложения (по исходникам)

1. **Большой монолитный интерфейс** — основной функционал находится в `index.html` (около 1,13 млн символов, сотни функций и много встроенных скриптов/стилей). Внутри несколько режимов и реализаций чек-листов, поэтому глобальный рефакторинг рискован.
2. **Сохранение чек-листов** — данные хранятся преимущественно в `localStorage`; среди пространств имён есть `checklist_tt_v1`, `checklist_msud_v1`, `checklist_hydro_v1`, а также другие ключи для отдельных форм/режимов. Ключи нельзя переименовывать или очищать без отдельной миграции.
3. **Фотографии** — используется IndexedDB с базой `checklist_photos_db` и хранилищем `photos`; есть функции восстановления/переноса фото. Ключи фотографий связаны с идентификаторами чек-листов и полей, поэтому перенос данных должен сохранять эти связи.
4. **Пользовательский интерфейс авторизации** — текущая авторизация работает на клиенте и использует `localStorage`. Любой непустой логин, кроме неуспешной попытки входа под администратором, может получить обычную пользовательскую роль. Это не серверная аутентификация и не граница безопасности; права доступа нельзя защищать только скрытием кнопок.
5. **Интеграция GitHub** — конфигурация по умолчанию указывает на репозиторий `volchonok16161-droid/prilogenia`, ветку `main` и файлы `oborudovanie.json` / `zona_riska.xlsx`. Перед изменением этой интеграции нужно исключить запись в рабочую ветку из тестовых сценариев и не сохранять токены в исходниках.
6. **PWA / офлайн** — `manifest.json` задаёт устанавливаемое приложение. `sw.js` использует кэш `checklist-cache-v19`, кэширует оболочку и ExcelJS с CDN при доступной сети; при активации удаляет кэши с другими именами. Данные пользователя в `localStorage` и IndexedDB этим кодом напрямую не удаляются, но обновление кэша требует отдельной проверки на уже установленных устройствах.
7. **Внешние ресурсы и импорт/экспорт** — ExcelJS загружается с CDN, а экспорт/импорт и фотографии — критичные пути. Импорт может заменить состояние, поэтому тестировать его только на копиях данных.

## Предлагаемая архитектура следующего этапа

- Сохранить существующие чек-листы и интерфейс; не переписывать монолит целиком.
- Добавить облачную аутентификацию и базу данных отдельным слоем (например, Supabase Auth + Postgres с RLS), после согласования модели ролей и доступа.
- Оставить локальное хранилище для офлайн-работы: IndexedDB для структурированных данных/очереди синхронизации, с отдельной схемой и версией миграции.
- Синхронизировать только явно выбранные типы данных; предусмотреть идентификаторы записей, автора/владельца, временные метки, версии и разрешение конфликтов.
- Не переносить автоматически существующие локальные данные в облако. Сначала резервная копия, предпросмотр и явное подтверждение пользователя.

## Базовый регрессионный чек-лист

Перед каждым изменением и после него, на копии данных:

- [ ] Открытие сайта онлайн и запуск уже установленного PWA офлайн.
- [ ] Создание нового чек-листа, продолжение сохранённого и переключение между режимами.
- [ ] Сохранение, перезагрузка страницы и проверка восстановления данных.
- [ ] Добавление/просмотр/удаление фотографии и восстановление после перезапуска.
- [ ] Валидация обязательных полей и числовых значений.
- [ ] Экспорт в JSON/Excel/HTML (где поддерживается), повторное открытие результата.
- [ ] Импорт корректного JSON; отклонение повреждённого/неподходящего файла без потери текущих данных.
- [ ] Работа конструктора оборудования/чек-листов и порядка оборудования.
- [ ] Проверка GitHub-функций только в тестовой ветке/на тестовых файлах; убедиться, что `main` не изменяется.
- [ ] Обновление Service Worker: приложение открывается, локальные данные и фотографии остаются.
- [ ] Android: установка, запуск без сети, повторное подключение.
- [ ] Windows: запуск в поддерживаемом браузере, офлайн-режим и восстановление после перезапуска.

## Условия перехода к реализации

1. Подтвердить перечень режимов и обязательных пользовательских сценариев с сотрудником/владельцем процесса.
2. Проверить существующие ключи и формат данных на обезличенной резервной копии.
3. Согласовать роли (администратор, сотрудник), принадлежность чек-листов и правила общих данных.
4. Сначала добавить безопасный диагностический/тестовый слой или отдельный прототип; затем интегрировать аутентификацию и синхронизацию небольшими изменениями.
5. Не сливать изменения в `main` и не публиковать их до прохождения регрессионных тестов и явного подтверждения.
