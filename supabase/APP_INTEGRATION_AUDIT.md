# Аудит подключения учётных записей к основному приложению

Дата аудита: 2026-10-30  
Рабочая ветка: `development/account-system`

## Результат проверки

Пока подключение к основному интерфейсу **не выполнено**. Авторизация Supabase и функция `account-admin` работают отдельно в тестовой панели. Нельзя считать, что сотрудники уже входят в основное приложение или что их чек-листы разделены.

Проверка исходного `index.html` выполнена по Git blob, так как файл слишком большой для обычного `fetch_file`. Файл — монолит примерно 1,276,072 байта; в нём есть основной интерфейс и несколько HTML-шаблонов встроенных чек-листов.

## Найденные точки риска

1. **Старая авторизация небезопасна.** `doLogin` принимает любой непустой логин/пароль для обычного пользователя; роль и сессия сохраняются в `localStorage.checklist_user`. Отдельные admin/developer проверки основаны на локальных хэшах. Эти данные не являются доказательством личности и должны быть заменены Supabase Auth + серверным профилем.
2. **Состояние чек-листа общее для браузера.** Ключ `checklist_tt_v1` один для всех пользователей на одном origin. `showContinueDialogOrStart`, `loadState`, `saveState` и `fullClearState` обращаются к нему напрямую.
3. **Автосохранение регулярно выполняется.** `saveState(true)` запускается примерно каждые 20 секунд и при `beforeunload`. Переключение аккаунта без блокировки/сброса контекста может записать данные предыдущего пользователя под следующим аккаунтом.
4. **Фотографии имеют отдельное хранилище.** IndexedDB база `checklist_photos_db`, store `photos`; ключи имеют формат `checklist_tt_v1::itemId::photoField`. Сейчас ключ не содержит ID пользователя, поэтому фотографии тоже необходимо разделить.
5. **Есть встроенные HTML-копии чек-листов.** В `index.html` обнаружены шаблоны `EMBED_TT_HTML`, `EMBED_BI_HTML`, `EMBED_HYDRO_HTML` и `EMBED_CHECKLIST_HTML`, а также iframe `embeddedFrame`. Интеграция только в родительскую страницу не гарантирует, что вложенный чек-лист использует ту же сессию и изолированное хранилище.
6. **Облачная модель ещё не проверена end-to-end.** Таблица `public.checklists` и RLS описаны в `schema.sql`, но наличие SQL в репозитории не подтверждает, что отрицательные тесты A/B пройдены. Фотографии в Supabase Storage и политики Storage ещё не подготовлены.

## Безопасная целевая схема

- Supabase Auth выполняет вход по Email/Password.
- После входа клиент читает профиль текущего пользователя; роль берётся из `profiles.role`, а не из localStorage или полей формы.
- Разработчик/администратор видит панель управления. Сотрудник сразу попадает в привычный выбор/интерфейс чек-листа.
- Облачные записи сохраняются в `public.checklists`; `owner_id` берётся из проверенной сессии (`auth.uid()`) и защищается RLS.
- Локальный кэш и IndexedDB получают отдельное пространство имён с UUID пользователя. При выходе автосохранение текущего пользователя завершается до очистки контекста.
- Старые данные под ключом `checklist_tt_v1` остаются нетронутыми. Их нельзя автоматически присваивать первому вошедшему сотруднику; нужен явный экран предварительного просмотра/импорта с подтверждением владельца.
- Фото сначала остаются локально изолированными; облачная передача фото добавляется отдельным этапом через приватный Storage bucket и политики, ограниченные папкой пользователя.

## Порядок внедрения

### Этап 1 — обязательные проверки безопасности
- Прогнать RLS отрицательные тесты с двумя разными Auth-пользователями.
- Убедиться, что A не читает/не меняет/не удаляет строки B и не может подменить `owner_id`.
- Убедиться, что сотрудник не может читать/изменять роль профиля и не может вызвать административные действия.
- Проверить блокировку Auth-пользователя и отзыв/обновление сессии.

### Этап 2 — клиентский модуль авторизации
- Добавить отдельный модуль Supabase-клиента без секретных ключей.
- Заменить старую проверку логина на `signInWithPassword`, затем проверить профиль и роль.
- Удалить обход «любой логин/пароль» и локальные admin/developer хэши только после того, как новый вход проверен в тестовой версии.
- Обеспечить единый session bridge для родительской страницы и всех встроенных iframe.

### Этап 3 — изоляция локального состояния
- Ввести user-scoped ключи для LocalStorage и IndexedDB.
- Перехватить/обновить сохранение, загрузку, очистку и автосохранение во всех шаблонах.
- Добавить безопасный переход между аккаунтами и явный импорт старых данных.

### Этап 4 — облачная синхронизация
- Синхронизировать метаданные и JSON payload в `public.checklists`.
- Ввести защиту от конфликтующих обновлений по `revision`/времени обновления.
- Подготовить приватный Storage для фотографий, отдельные политики и проверку владельца.
- Проверить работу без сети, повторное подключение и восстановление с другого устройства.

### Этап 5 — приёмка
- Проверить сценарии developer/admin/employee, A/B isolation, logout/login, автосохранение, переключение режимов, фотографии, импорт старых данных.
- Только после успешной приёмки обсуждать перенос изменений в `main`.

## Ограничения текущего этапа

- `main` и опубликованный GitHub Pages сайт не изменялись.
- Ни один существующий локальный чек-лист или фото не мигрировал и не удалялся.
- Не добавлялись секретные ключи в HTML, JS или Git.
- Текущая рабочая ветка опережает `main`; дальнейшие изменения остаются только в `development/account-system`.
