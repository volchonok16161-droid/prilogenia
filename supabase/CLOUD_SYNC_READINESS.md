# Аудит готовности облачной синхронизации

Дата проверки: 2026-11-02  
Рабочая ветка: `development/account-system`

## Итог

Авторизация Supabase и локальная изоляция по UUID уже реализованы в интерфейсе. Однако **полноценная облачная синхронизация чек-листов ещё не подключена**: в текущем `index.html` нет обращений к таблице `public.checklists` или записи состояния через Supabase Data API. Основные рабочие данные пока хранятся локально в LocalStorage и IndexedDB.

Не включать автоматическую миграцию или загрузку старых локальных данных в облако до отдельного проектирования и согласования.

## Состояние проекта Supabase

- Проект доступен и имеет статус `ACTIVE_HEALTHY`.
- Регион: `eu-west-1`.
- В `public.profiles` включён RLS; таблица содержит 4 профиля.
- В `public.checklists` включён RLS; таблица содержит 4 строки.
- В текущей истории миграций, возвращённой Supabase, записей нет. Это требует сверки с репозиторием и не доказывает отсутствие ранее выполненных ручных SQL-изменений.
- Клиентский модуль использует publishable key; service_role key в клиентский код добавлять нельзя.

## Проверенные политики RLS

`profiles`:
- SELECT только строки, где `id = auth.uid()`.
- Клиентской роли `authenticated` не выданы INSERT, UPDATE или DELETE.

`checklists`:
- SELECT и DELETE ограничены `owner_id = auth.uid()`.
- INSERT требует `owner_id = auth.uid()`.
- UPDATE содержит и `USING`, и `WITH CHECK` на `owner_id = auth.uid()`.

Также проверены grants: `authenticated` имеет необходимые CRUD-права на `checklists` и только SELECT на `profiles`. Само наличие grants не отменяет ограничений RLS.

## Проверка изоляции на стороне БД

Выполнены две read-only проверки в транзакциях с откатом, с ролью `authenticated` и разными тестовыми значениями JWT subject:

| Проверка | Тестовый пользователь A | Тестовый пользователь B |
|---|---:|---:|
| Видимые строки profiles | 1 | 1 |
| Видимые собственные profiles | 1 | 1 |
| Видимые строки checklists | 0 | 0 |

Результат согласуется с политиками RLS: каждый пользователь видит только собственный профиль; чужие профили скрыты. В таблице чек-листов тестовых записей для этих субъектов не найдено.

Ограничение проверки: это SQL-проверка контекста роли и JWT claim, а не полноценный браузерный вход двумя реальными пользователями и не проверка запросов из клиентского SDK.

## Выявленный пункт безопасности

Supabase Security Advisor сообщил: **Leaked Password Protection Disabled**. Рекомендуется включить проверку паролей на утечки в настройках Auth проекта. Это изменение настройки Auth не выполнялось в рамках данного аудита.

## Что нужно сделать перед облачной синхронизацией

1. Согласовать формат облачного payload и перечень режимов чек-листа.
2. Подключить чтение/создание/обновление/удаление `checklists` через Supabase JS с пользовательской сессией.
3. Добавить revision-based optimistic concurrency или иной механизм защиты от перезаписи параллельных изменений.
4. Отдельно спроектировать хранение фотографий в Supabase Storage с политиками доступа по владельцу. Не складывать фото в общедоступный bucket.
5. Определить безопасную стратегию offline-first: очередь, повторы, конфликтующие записи, выход и смена аккаунта.
6. Написать интеграционные тесты, которые выполняют реальные запросы от двух тестовых аккаунтов и проверяют запрет чтения/изменения чужих строк.
7. Только после этого планировать импорт старых локальных данных — исключительно по явному действию пользователя.

## Границы изменений

В ходе аудита не изменялись таблицы, RLS-политики, пользователи, данные, Storage buckets или настройки Auth. Никакие локальные данные не переносились и не удалялись.
