# Прототип серверной модели (Supabase)

Это схема для ревью, а не готовое production-развёртывание. Она не подключена к приложению и не содержит ключей/секретов.

## Принятые правила

- Один сотрудник видит, создаёт, изменяет и удаляет только собственные чек-листы.
- Администратор управляет созданием учётных записей через доверенную серверную функцию.
- Роль нельзя назначить или изменить из браузера.
- Администратор не получает автоматический доступ к содержимому чужих чек-листов: это отдельное бизнес-решение, здесь доступ строго по `owner_id`.
- Локальный `ownerId` в прототипе IndexedDB не является подтверждённой личностью. В реальной синхронизации владелец должен определяться по проверенному JWT на сервере, а не по значению из запроса.

## Файлы

- `supabase/schema.sql` — таблицы профилей и чек-листов и политики RLS.
- `supabase/README.md` — порядок безопасного внедрения и нерешённые вопросы.

## До применения схемы

1. Создать отдельный тестовый проект Supabase, не использовать production-проект.
2. Прочитать SQL и проверить политики через тестовые учётные записи двух сотрудников.
3. Добавить серверную Edge Function для создания пользователя администратором. Функция должна проверять JWT вызывающего пользователя и роль администратора на сервере, валидировать ввод, ограничивать частоту запросов и использовать service_role только в серверных секретах.
4. Настроить создание профиля без возможности назначать себе роль. Начальную роль администратора устанавливать вручную доверенной процедурой.
5. Проверить отрицательные сценарии: сотрудник A не может прочитать/изменить/удалить записи B, подставить чужой owner_id, повысить себе роль или вызвать создание пользователя без роли admin.
6. Только после этого проектировать клиентскую интеграцию и синхронизацию с IndexedDB.

## Что схема пока не решает

- Создание пользователей, сброс паролей, блокировка и восстановление доступа.
- Автоматическое создание профиля при регистрации Auth-пользователя.
- Обработка конкурентных обновлений и конфликта локальной/облачной версии.
- Проверка структуры JSON в `payload`, лимиты размера и аудит действий.
- Фотографии и файлы: для них нужна отдельная Storage-политика с путями, содержащими user ID, и проверкой владельца.
- Резервное копирование, хранение сроков, журналирование и политика удаления.

SQL нельзя считать проверенным только потому, что он сохранён в GitHub. Его необходимо применить к отдельному тестовому проекту и прогнать проверки RLS.
