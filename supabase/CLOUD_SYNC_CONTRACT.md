# Контракт облачного слоя чек-листов

Файл `prototype/supabase-cloud-sync.js` — изолированный слой доступа к `public.checklists`. Он не подключён автоматически к существующим обработчикам интерфейса и не импортирует данные LocalStorage/IndexedDB.

## Использование

После загрузки `prototype/supabase-auth.js`:

```js
import { createCloudSync } from "./prototype/supabase-cloud-sync.js";

await window.TMHAuthReady;
const cloud = createCloudSync(window.TMHAuth);
const records = await cloud.list();
```

Передача owner ID от UI не предусмотрена: владелец вычисляется заново через `TMHAuth.getCurrentIdentity()` для каждой операции.

## API

- `list()` — получить записи текущего владельца.
- `create({ title, equipmentType, payload })` — создать запись, owner_id берётся из сессии.
- `update({ id, expectedRevision, title, equipmentType, payload })` — обновить только при совпадении revision.
- `remove(id)` — удалить только запись текущего владельца.

## Конкурентные изменения

Обновление использует compare-and-swap: `id + owner_id + revision`. Revision увеличивается на единицу. Если другая сессия уже обновила запись или запись удалена, возвращается `REVISION_CONFLICT`; автоматическая перезапись не выполняется.

## Ограничения

- Payload ограничен 512 КБ и должен быть JSON-объектом.
- Inline base64 изображения запрещены. Фотографии требуют отдельной интеграции с Supabase Storage и приватными RLS-политиками.
- Этот модуль пока не решает offline queue, retry/idempotency, конфликтное слияние, миграцию локальных данных и привязку текущих пяти форматов чек-листов к облачному payload.
- Не считать облачную синхронизацию включённой в пользовательском интерфейсе до отдельной интеграции и browser E2E тестов.


## Защита на уровне базы данных

Миграция `supabase/migrations/20261102093000_checklist_revision_guard.sql` добавляет trigger, который:
- запрещает менять `owner_id` после создания строки;
- устанавливает revision=1 при вставке;
- требует при UPDATE ровно `old.revision + 1`;
- устанавливает `updated_at` на стороне БД.

Миграция добавлена в репозиторий. Повторная read-only проверка подключённого Supabase-проекта fecigiwjtbtabnsfsdym 2026-11-02 подтвердила, что trigger checklists_revision_guard активен на public.checklists, а функция public.enforce_checklist_revision() совпадает по ключевой логике с миграцией: owner неизменяем, revision увеличивается ровно на 1, updated_at задаётся БД. Серверный revision guard уже действует. Перед любым повторным применением миграции сначала сверять фактическую схему и migration history.


## Явная локальная резервная копия

Добавлен модуль `prototype/supabase-cloud-backup.js`. Его API `createChecklistCloudBackup({ authApi, storage, getState, getMode, getStorageKey }).saveCurrent()`:

- повторно подтверждает текущего пользователя через Supabase Auth;
- убеждается, что активный локальный ключ заканчивается UUID этой сессии;
- формирует payload с режимом и копией текущего состояния;
- удаляет из облачной копии поля, оканчивающиеся на `_photo`, не меняя исходное состояние;
- создаёт облачную запись при первом явном сохранении, затем обновляет её с ожидаемой revision;
- хранит ссылку на cloud row и revision в отдельном ключе того же пользовательского namespace;
- при конфликте или повреждённой ссылке останавливается и не создаёт незаметный дубликат.

**Это пока библиотечный адаптер, не кнопка в интерфейсе.** Он не запускается автоматически и не читает legacy namespace. Перед использованием в интерфейсе необходимо проверить интеграцию с каждым runtime, iframe/srcdoc и lifecycle приложения. Фото остаются локальными; отдельный модуль Supabase Storage ещё не реализован.


## Кнопка явного сохранения из встроенных режимов

В родительский интерфейс добавлена кнопка `☁️ Сохранить в облако` для пяти встроенных режимов. Кнопка добавляется к footbar при подготовке srcdoc, а bridge передаёт модулю резервирования текущее состояние, режим и пользовательский локальный ключ.

Сохранение выполняется только по нажатию. После запроса показывается результат или ошибка; при конфликте версии локальная ссылка не обновляется. Фотографии остаются в IndexedDB и не загружаются в облако.

Важно:
- это явная резервная копия, не фоновая двусторонняя синхронизация;
- текущая копия создаётся или обновляется по локальной ссылке на облачную строку;
- удалённые записи автоматически не загружаются в интерфейс;
- Storage для фото ещё не подключён;
- перед эксплуатацией необходимо проверить пять режимов в браузере на двух тестовых аккаунтах.

## Явное восстановление из облака

Добавлен модуль `prototype/supabase-cloud-restore.js`:

- `listAvailable()` возвращает только безопасные метаданные доступных текущему пользователю записей, без payload;
- `restore(id)` повторно проверяет сессию и получает запись по id через owner-scoped `cloud.get()`;
- payload проверяется, а режим должен совпадать с открытой формой;
- состояние клонируется и передаётся в явно переданную UI-функцию `applyState(state, metadata)`;
- модуль сам не пишет в LocalStorage/IndexedDB и не меняет локальные фотографии.

Пример подключения в UI:

```js
import { createChecklistCloudRestore } from "./prototype/supabase-cloud-restore.js";

const restore = createChecklistCloudRestore({
  authApi: window.TMHAuth,
  getMode: () => currentMode,
  applyState: async (state) => {
    // Здесь UI должен сначала показать подтверждение,
    // сохранить текущую локальную копию и только затем применить state.
    applyChecklistState(state);
  },
});

const backups = await restore.listAvailable();
// По явному выбору пользователя:
await restore.restore(backups[0].id);
```

**Важно:** это готовый библиотечный слой, не включённая в интерфейс кнопка. Подключение к пяти runtime-формам требует отдельно реализовать подтверждение перезаписи, безопасное обновление состояния без удаления IndexedDB-фотографий, сохранение локальной версии и browser E2E. Не считать восстановление доступным пользователям до этих работ.


## Подключение восстановления в основном интерфейсе (2026-11-02)

В `index.html` для нативных режимов `complex` и `housings` добавлена кнопка «Восстановить из облака».

Порядок работы:
1. Пользователь подтверждает открытие списка облачных копий.
2. Список содержит только записи текущего Supabase-пользователя.
3. Пользователь выбирает запись по номеру; другой режим отклоняется.
4. Перед применением текущий локальный чек-лист сохраняется отдельной облачной копией с названием «Автокопия перед восстановлением».
5. Затем состояние восстанавливается. Поля фотографий из текущего локального состояния объединяются с облачным состоянием, отсутствующие фото не удаляются.
6. Локальное состояние сохраняется штатным `saveState`, включая существующий механизм IndexedDB, после чего интерфейс перерисовывается.

Это первое подключение UI и пока ограничено нативными режимами `complex` и `housings`. Встроенные iframe-режимы `tt`, `bi`, `hydro` ещё не подключены. Облачные копии не содержат фотографии; восстановление фотографий с другого устройства не реализовано.

CI подтверждает 75 source-level тестов. Реальный браузерный сценарий с двумя устройствами/аккаунтами и проверка фотографий в браузере ещё не выполнены. Не считать это доказательством полного E2E.

После успешного локального сохранения локальная ссылка `::cloud-ref` переключается на восстановленную облачную запись и её revision. Следующие нажатия «Сохранить в облако» обновляют именно восстановленную запись через compare-and-swap, а не прежнюю копию.


## Восстановление для встроенных режимов (2026-11-02)

В функцию `__tmhAttachCloudBackup(source, mode)` добавлена кнопка «Восстановить из облака» для встроенных iframe-режимов ТТ (`tt`), БИ (`bi`) и гидродемпферов (`hydro`). Восстановление использует Auth-сессию родительской страницы, отбирает записи только с совпадающим `payload.mode`, создаёт отдельную облачную safety-копию текущего локального состояния перед применением, сохраняет локальные `_photo` поля и обновляет ссылку `::cloud-ref` с revision восстановленной записи. Кнопка действует только внутри активного iframe-режима.

CI: 80 source-level тестов пройдены, 0 ошибок. Это не браузерный E2E: реальный выбор режима, подтверждение восстановления, работа IndexedDB и фактическая загрузка данных между устройствами ещё требуют ручной проверки в браузере. Фотографии между устройствами по-прежнему не синхронизируются.
