# Матрица проверок RLS и учётных записей

Эта матрица предназначена для отдельного тестового проекта. Не использовать рабочие данные и не применять SQL к production-проекту.

## Подготовка

0. Создать отдельный Supabase test project и сверить его project ref в URL Dashboard. Запрещён Production ref `fecigiwjtbtabnsfsdym`. В репозитории этот ref используется приложением как Production endpoint; он не является тестовым. Не использовать реальные Auth UUID и данные сотрудников.

Создать две обычные учётные записи Employee A и Employee B. Создать их через тестовый Auth-процесс. Для каждого пользователя создать по одной записи с уникальным текстовым маркером. Не использовать service_role в браузере.

## Обязательные проверки

| Сценарий | Действие | Ожидаемый результат |
|---|---|---|
| Чтение своих данных | A читает список чек-листов | Видит только запись A |
| Чтение чужих данных | A запрашивает запись B по ID | Нет строки / доступ не предоставлен |
| Подмена владельца при вставке | A вставляет строку с owner_id=B | Операция отклонена политикой RLS |
| Подмена владельца при обновлении | A меняет owner_id своей записи на B | Операция отклонена |
| Удаление чужой записи | A удаляет запись B по ID | Запись B остаётся на месте |
| Неавторизованный запрос | Запрос без сессии | Доступ запрещён |
| Изменение роли | A пытается обновить profiles.role | Операция отклонена |
| Создание аккаунта сотрудника | Employee A вызывает административную функцию | HTTP 403 / доступ запрещён |
| Создание аккаунта администратором | Администратор вызывает функцию с валидными данными | Аккаунт создаётся, роль выдаётся доверенным серверным кодом |
| Подмена роли в запросе | A передаёт role=admin | Роль не повышается |
| Повторная отправка | Клиент повторяет тот же запрос | Нет случайного дублирования или несанкционированного изменения |
| Удалённая/заблокированная учётная запись | Сессия пользователя отозвана | Новые запросы не дают доступ |

## Критерий допуска

Все отрицательные тесты должны пройти: пользователь не читает и не меняет чужие записи, не может повысить роль и не может создавать аккаунты. Любой провал блокирует подключение к рабочему приложению.

## Примечание

Эта матрица — план тестирования, не свидетельство того, что тесты уже выполнены. Проверки нужно запускать после применения схемы в отдельном тестовом проекте Supabase.

## Дополнительная проверка отозванной Auth-сессии

В feature подготовлена миграция `20261111160000_revoked_session_rls_guard.sql`. Она не применена к Production и не должна применяться туда в рамках этой работы.

После применения только в отдельном тестовом проекте проверить:

| Сценарий | Действие | Ожидаемый результат |
|---|---|---|
| Активная сессия | A читает собственный чек-лист | Доступ разрешён |
| Отозванная сессия | Сервисная тестовая операция удаляет запись A из `auth.sessions`, затем A повторяет запрос с прежним access JWT | RLS возвращает 0 строк / запрещает изменение |
| Чужая сессия | JWT содержит session_id пользователя B, subject пользователя A | Доступ запрещён |
| Истёкшая сессия | `auth.sessions.not_after` в прошлом | Доступ запрещён |
| Фото | A скачивает фото после отзыва своей сессии | Storage RLS запрещает запрос |
| Экспорт | A скачивает Excel после отзыва своей сессии | Storage RLS запрещает запрос |
| Edge Function | Удалённый/отозванный администратор вызывает `account-admin` | HTTP 401, код `AUTH_SESSION_REVOKED` |
| Удаление аккаунта | Разработчик удаляет тестового сотрудника | Все refresh-сессии сотрудника отозваны до удаления Auth-пользователя; старые access JWT не проходят RLS |

Важно: удаление строки сессии не переписывает JWT и не блокирует SQL, который намеренно обходит RLS через service_role. Поэтому все privileged Edge Functions обязаны самостоятельно проверять активную сессию вызывающего пользователя до service-role операций. В текущей feature-функции `account-admin` такая проверка добавлена через service-only RPC.

## Локальные данные при удалении аккаунта

Backend не имеет доступа к IndexedDB на устройствах сотрудника. Поэтому проверка отсутствия облачных чек-листов и Storage объектов не доказывает, что локальные изменения/фото синхронизированы. Перед удалением разработчик должен получить подтверждение сохранности данных; интерфейс теперь явно предупреждает об этом. Нельзя автоматически удалять локальную IndexedDB или очереди при удалении Auth-пользователя.

## Сценарии IndexedDB и аварийного восстановления

Существующие автоматические тесты в feature:

- `tests/offline-vault-db-isolation.test.mjs`: compound keys по userId, очередь/конфликты по владельцу, fencing token и атомарная запись очистки фото.
- `tests/offline-vault-local-signout.test.mjs`: logout marker, гонка async recovery, смена аккаунта в другой вкладке, проверка контекста после await.
- `tests/offline-sync-runner.test.mjs`: аренда очереди, восстановление create после неопределённого результата, конфликт вместо перезаписи, повтор после временного сбоя.
- `tests/offline-photo-sync-integration.test.mjs` и `tests/supabase-cloud-photos.test.mjs`: rollback частичной загрузки, owner path validation, abort при смене аккаунта во время upload/download.

Эти тесты моделируют IndexedDB/Auth/Storage-контракты. Они не заменяют браузерное испытание реальными двумя тестовыми аккаунтами и отдельным тестовым Supabase-проектом.
