# Управление аккаунтами сотрудников

Edge Function: `account-admin`.

## Текущий статус (проверка ветки `development/account-system`, 2026-11-02)

- В Supabase проекте `prilogenia` функция `account-admin` числится активной (версия 1). Это подтверждает наличие развёрнутой функции, но не доказывает, что её код совпадает с текущим файлом в этой ветке.
- В `account.html` подключены просмотр списка сотрудников и блокировка/восстановление доступа через `account-admin`.
- Форма приглашения сотрудника в `account.html` пока отсутствует. Серверная ветка `invite_employee` есть в коде репозитория, но реальная отправка письма не проверялась.
- Сквозные проверки с реальными тестовыми пользователями и письмами не выполнялись.

## Доступные действия в коде функции

Все запросы — POST с заголовком `Authorization: Bearer <access_token>` и JSON:
- `{"action":"list_employees"}` — список сотрудников.
- `{"action":"invite_employee","email":"...","display_name":"..."}` — приглашение сотрудника по email.
- `{"action":"set_employee_access","user_id":"<uuid>","suspended":true}` — заблокировать вход.
- `{"action":"set_employee_access","user_id":"<uuid>","suspended":false}` — восстановить вход.

## Защита

- Функция проверяет JWT через Supabase Auth и роль вызывающего пользователя по серверной таблице `profiles`.
- Только роли `developer` и `admin` могут выполнять операции.
- Service role используется только внутри Edge Function.
- Сотруднику можно менять доступ только к аккаунту с ролью `employee`.
- Профили не должны быть доступны для записи из браузера.

## Обязательные задачи до включения приглашений

1. Определить и подтвердить основной публичный origin приложения. Не использовать URL страницы восстановления пароля в качестве адреса кабинета.
2. Добавить серверную конфигурацию `APP_SITE_URL` и передавать в `inviteUserByEmail` явный `redirectTo` на кабинет приложения. Значение должно проверяться по allowlist; не принимать redirect URL от браузера.
3. Проверить, что callback разрешён в Supabase Auth Redirect URLs и что письмо приводит пользователя в PKCE callback.
4. Проверить наличие триггера на `auth.users`, чтобы не создать конфликт при upsert профиля.
5. Проверить SMTP/шаблон приглашения и провести тест на отдельном тестовом адресе только после согласования.
6. Устранить гонку лимита в 15 сотрудников: текущая проверка count выполняется до создания пользователя и не атомарна при параллельных приглашениях. Нужна транзакционная серверная операция/блокировка.
7. Проверить повторное приглашение существующего пользователя и откат Auth-пользователя при ошибке создания профиля.
8. Протестировать вызовы под developer, admin и employee; employee должен получать 403.

## Важное

- Не считать приглашения готовыми к использованию, пока не подтверждены callback и фактическое получение письма.
- Не помещать `SUPABASE_SERVICE_ROLE_KEY` в браузер, HTML, репозиторий или сообщения.
- Не запускать реальные приглашения без тестового адреса и согласованного сценария.
